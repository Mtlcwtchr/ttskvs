# KVS TTS Platform — правила проекта

Мод Tabletop Simulator: платформа для отыгрыша RP по миру КВС (Край Вечных Сказаний).

## Разработка

- Редактор: VS Code + расширение `sebaestschjin.tts-editor` ("Tabletop Simulator Editor").
- Команды: `Get Objects` (вытянуть скрипты из запущенного TTS в `.tts/objects/`), `Save and Play` (отправить `src/` обратно в TTS с автобандлингом `require()`/`<Include/>`, хот-релоад).
- `includePath` = `src` — **не дефолт**: дефолт расширения `.` (корень воркспейса), при нём `require("Global")` не резолвится (`Could not resolve module 'Global' required by '__root'`). Значение прописано в `.vscode/settings.json` (`ttsEditor.includePath`), файл должен быть в репозитории.
- TTS должен быть запущен с загруженным сейвом (`Saves/KVS/`) — иначе Get Objects/Save and Play не с кем говорить (localhost:39999/39998).
- Запасной инструмент: `tools/tts_bridge.py` (pull/push/watch) — тот же протокол напрямую, без VS Code. Не запускать одновременно с активным расширением — конфликт по порту 39998.

**Капканы тулчейна (уже наступали, не повторять):**
- Бандлер расширения (luabundle) резолвит модули **только** по `src/?.lua` и `src/?.ttslua`. `require("ui.components.layout.Button")` на `.xml`-файл он не найдёт, хотя `tts_bridge.py` такое умеет. Плюс песочница TTS не читает файлы в рантайме, а скрипт объекта в сейве — одна плоская строка, то есть текст XML обязан лежать внутри отправляемого Lua. Отсюда пара директорий: `ui/layout/**/*.xml` — исходники, `ui/generated/Templates.lua` — единый генерируемый модуль шаблонов.
- **Проверяйте вёрстку до отправки в игру:** `python3 tools/tts_bridge.py check-layout` (нужен `lua`, `brew install lua`). Он же вызывается из `push` и из задачи watch-xml после каждой правки XML — то есть терминал сам скажет, сошлась геометрия или нет, ещё до запуска TTS.
- **Правите `layout/**/*.xml`, `generated/` не трогаете.** Шаблоны пересобирает `python3 tools/tts_bridge.py sync-xml` (и автоматически — `push`), в фоне — задача VS Code «TTS: watch XML templates» из `.vscode/tasks.json`, стартующая при открытии папки (VS Code один раз спросит «Allow Automatic Tasks»). В обёртку попадает та же разметка **без XML-комментариев**: комментарии — документация для того, кто правит `layout/`, а в игру они уезжали бы копией на каждый инстанс (25 полей чарника — 25 копий шапки `InputField.xml`). `.xml` вне `layout/**` sync-xml не обслуживает и предупреждает об этом.
- `Get Objects` разбандливает скрипт из игры только если в нём есть метаданные luabundle. Бандл от `tts_bridge.py push` их не содержит, поэтому Get Objects после push кладёт **весь бандл целиком** в `.tts/objects/Global.lua`, затирая тонкий энтрипоинт `require("Global")`. Следующий `Save and Play` пытается бандлить бандл и падает на `require("Global")` в его последней строке (`... required by '__root' at 2119:0`). Лечится `git checkout -- .tts/objects/Global.lua`. Вывод: не смешивать push через bridge и Get Objects через расширение в одном цикле.
- `.tts/objects/Global.lua` — тонкий энтрипоинт из одной строки `require("Global")`, весь код Global живёт в `src/Global.lua`. `.tts/bundled/` — кеш расширения, генерируемый, руками не править.

## Правило 1 — Data-driven, обязательно

Игровой контент (персонажи, предметы, способности и т.д.) — это данные, а не ветвления в коде. Ни один конкретный персонаж/предмет не хардкодится в Lua как отдельная ветка логики. Скрипты пишут универсальные "шаблоны"/фабрики, которые инстанциируют что угодно из данных.

**Почему:** контент должен добавляться и правиться без переписывания скриптов.

## Правило 2 — JSON отдельно от скриптов, скрипты — это шаблоны ("классы")

- Исходные данные (персонажи, шаблоны предметов, способностей и т.д.) живут в `.json`-файлах, физически отдельно от Lua.
- Lua-скрипты не хардкодят данные — они **загружают** JSON и **инстанциируют** по нему объекты через общие шаблонные функции (аналог классов/фабрик).

**Загрузка в рантайме:** песочница TTS Lua не имеет доступа к диску во время игры — `.json`-файлы с диска не читаются напрямую. Выбранный механизм — **WebRequest**: JSON хостится по URL (детали хостинга — TODO, репозиторий `kvas` пока не под git), скрипт получает его через `WebRequest.get(url, callback)` и разбирает `JSON.decode(...)`.

Вся загрузка инкапсулирована в `src/core/DataLoader.lua` — остальной код зовёт `DataLoader.loadParty(callback)` и не знает, приходят данные по сети или из моков. Пока хостинг не настроен, `DataLoader` отдаёт `src/core/MockData.lua` за тем же интерфейсом — при переключении на реальный URL остальной код не меняется.

**`src/core/MockData.lua` — автогенерируемый файл, руками не редактировать.** Единственный источник — `data/characters/*.json` (один файл на персонажа). Изменили JSON → `python3 tools/tts_bridge.py sync-mock` пересобирает `MockData.lua` (это же происходит автоматически внутри `push`). Файл — не Lua-копия данных, а сырой JSON из тех файлов, склеенный в массив и обёрнутый в `JSON.decode([==[ ... ]==])` — визуально это просто ваш JSON. Раньше был инцидент: данные Миры существовали только в `MockData.lua`, без JSON — это и есть та ошибка, которую чинит генератор.

## Правило 3 — Два разных UI, не путать

- **HUD + лист персонажа** — постоянный игровой интерфейс поверх стола (Global UI, `visibility` по игроку, не привязан ни к одному объекту на столе). Полоска портретов партии сбоку (в духе Divinity/BG3), клик по портрету — выбор (подсветка рамкой и укрупнение плитки, как в 4A); лист выбранного персонажа открыт рядом. Нижний action rail из 4A — следующий шаг. Это основной экран во время игры.
- **Лист персонажа — один лейаут в двух режимах.** `view` — только чтение, это основной игровой вид (бумажный лист D&D 5e). `wizard` — тот же лейаут, но значения становятся редактируемыми `InputField` с теми же id; переключается кнопкой «Редактировать» / «Готово» в шапке. Кнопка «+» в рейке партии создаёт заготовку и **сразу открывает визард** — отдельного флоу создания персонажа нет. Клик по портрету всегда открывает `view`: игровой экран не должен превращаться в форму от одного тычка.
- Режим живёт в `Global.lua` (`sheetMode`) и передаётся в `UIBuilder.buildMainUI`; выбор контрола — в `ui/sheet/Field.lua`. Высоты секций одинаковы в обоих режимах намеренно: при переключении лейаут не должен прыгать.

## Дизайн-референс

Источник — Claude Design проект «BG3 and D&D Sheet Fusion», архив лежит в репозитории: `tools/BG3 and D&D Sheet Fusion.zip`, внутри `Adventurer HUD.dc.html`. Реализуется **секция 4A** («Ashgrave Codex · character window», 1600×1000): тёплое обожжённое золото по углю.

Что перенесено из 4A один в один:
- **Палитра** — `src/ui/Theme.lua`, значения скопированы из мокапа (золото `#d9b877`/`#efdcae`/`#f4e7cb`, латунь `#8a7048`, подписи `#b08d57`, подложки `#1a120c`/`#241a12`/`#2f2318`, слоты `#4a3826`, хиты `#cf5136`).
- **Место и размер окна** — 1004×620 с отступом 126/120 от левого верхнего угла, рейка партии у левого края (x=22, портреты 78 у выбранного / 72 у остальных, табличка хитов под плиткой).
- **Компоновка окна** — шапка с табличкой имени, дальше три колонки: столбик из шести плиток характеристик + список навыков с подписью СНИЗУ; кукла со слотами слева/справа и рядом ближний-броня-дальний; сумка сеткой 7 в ряд, блок способностей, два блока заметок рядом.

Чего в 4A нет, а у нас есть (оставлено, потому что элементы уже были): выносливость и мана рядом с хитами, чипы расы/класса/уровня/возраста/мировоззрения/игрока второй строкой шапки, кнопки «Редактировать/Готово/Закрыть/Удалить» на месте вкладок SHT/INV/SPL.

Чего в 4A есть, а у нас пока нет (добавляем следующими шагами, место под них в раскладке оставлено): полоса «порядок хода» сверху, панель броска и лог справа, нижний action rail с хотбаром и ячейками заклинаний, поиск и фильтры над сумкой, бонус мастерства и вдохновение, вес и кошель.

**Текущая стадия — плоская фидельность**: цвета и раскладка перенесены, а градиенты, внутренние тени, свечение, кованые уголки и хекс-обрезка плашек — нет (TTS XML не умеет ни того, ни другого без готовых PNG 9-slice текстур). Рамки поэтому сплошные: блок с `color="brass"` и `padding="1..2"`, внутри блок с фоном. Кастомные шрифты (Grenze Gotisch/Spectral) — TODO отдельным шагом (нужен хостинг .ttf под `UI.setCustomAssets`), пока шрифт TTS по умолчанию. Портрет и иконки предметов — заглушки (буква/подпись), реальные изображения требуют хостинга.

**Смотреть, что получилось, можно без TTS:** `lua tools/layout_preview.lua view > /tmp/v.html` (или `wizard`) рисует посчитанную геометрию в HTML — те же числа, что уедут в игру, каждый Panel прямоугольником, каждый Text строкой. Открыть в браузере или отрендерить в PNG:
`"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless --screenshot=/tmp/v.png --window-size=1600,1000 /tmp/v.html`.
Шрифт и автоподбор кегля там приблизительные, всё остальное — точное.

**Известные баги (уже исправлены, не повторять):**
- **Размеры в разметке руками больше не пишутся — их считает `src/ui/Layout.lua`.** Именно ручные размеры на каждом уровне и были причиной «правишь одно — едет другое»: `Sheet 1320 -> padding 16 -> Panel 1288 -> колонка 478 -> Box 466 -> плитка 148`, где ни одно число не выводилось из другого. См. раздел «Правило 6» ниже.
- **Абсолютное позиционирование — только `<Anchor>` и только на верхнем уровне.** Шапка листа была собрана из вложенных `<Anchor offset="1208 10">`: `offsetXY` считается от края, заданного `rectAlignment` (по умолчанию — от ЦЕНТРА), а y в TTS растёт ВВЕРХ, поэтому кнопки уезжали за пределы листа, а блоки наезжали друг на друга. Теперь `<Anchor x y>` принимает координаты «как везде» (y вниз), инвертирование и пересчёт под `rectAlignment` спрятаны в `Layout`.
- Составной элемент из двух соседей (подпись + поле) нельзя кидать прямо в `<Row>`: получится `[подпись][поле][подпись][поле]` в одну линию вместо двух пар. Такие пары — отдельный компонент со своим `<Col>` (`sheet/LabeledField.lua`, `sheet/HeaderChip.lua`).
- **У layout-групп нет ни размера, ни фона, и руками их писать нельзя.** По документации (api.tabletopsimulator.com/ui/layoutgrouping) у `VerticalLayout`/`HorizontalLayout` есть только `padding`/`spacing`/`childAlignment` (плюс `child*`-флаги); `color` на группе рисует фон ПОВЕРХ детей, `width` разваливает вёрстку целиком. Плюс `childControlWidth`/`childControlHeight` по умолчанию **true**, то есть группа переопределяет размеры детей. Поэтому группы (и сырой `<Panel>`) в разметке запрещены: их пишет `Layout` — всегда в одной конфигурации, все четыре `child*`-флага `false`, у детей уже посчитанные размеры. Ловится линтом `sync-xml`.
- **У Button и InputField цвет задаётся `colors`, а текст по умолчанию тёмный.** `colors` — это четыре состояния через `|` (normal|highlighted|pressed|disabled, дефолт БЕЛЫЙ), а `textColor` по умолчанию `#323232`: кнопка с тёмным фоном и без `textColor` — это тёмная надпись на тёмном фоне, а поле правки без `colors` — белая заплатка на листе. Плюс `textAlignment` у Button по умолчанию `UpperLeft`. Всё это задано разом в `<Defaults>` в начале `MainUI.xml` (api.tabletopsimulator.com/ui/defaults) и в ролях `Theme.buttonStates`/`Theme.inputStates`.
- **`lineType` у InputField — только `SingleLine`/`MultiLineSubmit`/`MultiLineNewLine`.** Прежнее `MultiLine` невалидно, TTS молча игнорировал его, и многострочные поля оставались однострочными.
- **Русский текст не влезает там, где влезал английский** (он на 15–20% длиннее), а `horizontalOverflow` у TTS по умолчанию `Overflow` — то есть строка не переносится, а вылезает поверх соседей. Поэтому `Layout` дописывает каждому `<Text>` автоподбор кегля (`resizeTextForBestFit` с `resizeTextMaxSize` = заданный кегль: расти нельзя, сжаться до 62% можно, порог — `Layout.metrics.minFontRatio`), а описаниям в списках ставится `wrap="true"` (`horizontalOverflow="Wrap"`). Если подпись всё равно нечитаема — она просто слишком длинная для клетки: сокращайте текст или расширяйте колонку, автоподбор это только страховка.
- **Число из атрибута разметки приводится к числу только если запись не теряется.** `tonumber("+2")` = 2, и модификатор характеристики приезжал в плитку без плюса. Теперь `Markup.parseAttributes` оставляет строку, если `tostring(tonumber(v)) ~= v`.
- **Прозрачная панель на весь экран съедает клики по столу**: `raycastTarget` по умолчанию `true`. Корневому блоку (`width="fill" height="fill"` на верхнем уровне) `Layout` дописывает `raycastTarget="false"` и не пишет размер вовсе — `width`/`height` по умолчанию `100%`, так что панель сама растягивается по холсту любого разрешения.
- **Несколько детей в `<Box>` лежат друг на друге.** Это его смысл (подложка + оверлей), но список из трёх строк, положенный в `<Box>`, схлопнется в одну: строки — это `<Col>`. Проверка геометрии такой случай не ловит (наложение в блоке без потока законно) — видно на предпросмотре.
- В `rgba(r,g,b,a)` r/g/b — тоже 0..1 float, **не** 0..255 (в отличие от CSS!). `rgba(20,16,10,0.96)` — невалидные значения, парсер их не принимает, и фон остаётся полностью прозрачным (виден стол под UI, лист персонажа выглядел "развалившимся"). Все rgba-константы — в `Theme.lua` (`Theme.overlayDark`, `Theme.sheetBg`), уже в правильном диапазоне.

## Правило 6 — размеры объявляются намерением, пиксели считает Layout

Инструмент вёрстки — пять примитивов и пять способов задать размер. Ничего другого в разметке нет.

```xml
<Row width="fill" height="132" padding="12" gap="16" align="left">   <!-- строка -->
  <Box width="104" height="fill" color="bgTile"/>                    <!-- блок -->
  <Col width="fill" height="fill" gap="8" align="topleft"/>           <!-- столбец -->
  <Scroll width="fill" height="fill" gap="4"/>                        <!-- окно прокрутки -->
</Row>
<Anchor at="left" x="60" y="0" width="140" height="auto"/>            <!-- абсолютно -->
```

| размер | смысл |
| --- | --- |
| `240` | ровно 240 пикселей |
| `fill` | весь остаток вдоль потока (поровну с такими же), поперёк — весь размер родителя |
| `2fr` | как `fill`, но с весом: `2fr` получит вдвое больше, чем `1fr` |
| `50%` | доля внутреннего размера родителя |
| `auto` | по содержимому (сумма детей вдоль потока, максимум поперёк) |

Плюс `<Defaults>` — не элемент, а таблица базовых атрибутов для всего, что ниже (лежит в начале `MainUI.xml`): раскладка его не трогает, он уезжает в игру как есть.

Общее у всех примитивов: `width`, `height`, `padding` (`"8"` | `"8 12"` | `"8 12 4 6"` — left right top bottom), `color`, `id`, `at` (куда прижаться внутри `Box`/`Anchor`). У `Row`/`Col`/`Scroll` ещё `gap` и `align` (`topleft`/`top`/`left`/`center`/…). У `Anchor` — `x`/`y`, где **y растёт вниз**.

Почему так, а не как было: TTS не умеет считать раскладку так, как нам надо (размер живёт только на `Panel`, а layout-группа переопределяет размеры детей), поэтому раньше каждое число писалось руками на каждом уровне вложенности и ничего ни из чего не выводилось. Теперь `src/ui/Layout.lua` разбирает готовое дерево, считает всем конкретные пиксели и печатает TTS XML, где у каждого элемента размер уже стоит, а группы всегда в одной конфигурации. Отсюда гарантии:

- соседи делят место, поэтому **наехать друг на друга не могут**;
- изменение одного числа пересчитывает всё, что от него зависит (ширина листа → колонки → секции → плитки);
- если фиксированные дети не влезли — это сообщение с именем контейнера и числами, а не молчаливый наезд;
- опечатка в атрибуте (`heigth`, `gepth`) — ошибка, а не проигнорированный атрибут.

**Проверка без TTS — обязательный шаг.** `python3 tools/tts_bridge.py check-layout` (он же внутри `push`, он же после каждой правки в задаче watch-xml) собирает весь UI в обоих режимах и проверяет, что ничего не наезжает, не вылезает за родителя и не получило нулевой размер. `lua tools/layout_check.lua --dump` печатает дерево с посчитанными рамками (`Row 1328x132 @ 296,56`) — это и есть ответ на вопрос «а какого размера получилось на самом деле». `--xml` печатает готовый XML.

Крайние случаи, о которых стоит помнить:
- Ширину текста измерить нечем, поэтому у листьев (`Text`, `InputField`, `Button`) `width` по умолчанию `fill`, а `height` — `auto` (строка по кеглю, поле — `Layout.metrics.InputField`). Значит `auto` по ширине у контейнера с текстом внутри даст 0 — тексту нужен `fill` или число.
- Значение, приходящее из Lua (`{{VALUE}}`), кладётся в ячейку с явным размером (`<Box width="fill" height="fill">{{VALUE}}</Box>`): так и текст, и поле правки занимают одно и то же место, и лейаут не прыгает при переключении режима.
- Естественные высоты (строка = кегль × `lineFactor`, кнопка, поле, ширина скроллбара) — в одной таблице `Layout.metrics`.

## Правило 5 — UI собирается из компонентов, а не из копипасты разметки

Компонент — это «понимание некой кнопки/поля/секции»: разметка + дефолты. Конкретная кнопка — не своя разметка, а вызов компонента с нужными props.

```
src/ui/
  Component.lua                 # движок: подстановка {{KEY}} + слияние props с дефолтами
  components/
    layout/    Button.xml       # разметка (правите вы)
    generated/ Button.lua       # обёртка (генерируется, не редактировать)
    Button.lua                  # контракт: defaults + render(props)
```

- У каждого `layout/X.xml` есть `components/X.lua` с таблицей `X.defaults` — единственное место, где живут размеры, цвета (из `Theme.lua`) и кегль. Плейсхолдеры `{{UPPER_SNAKE}}` в разметке отображаются в props компонента явным списком в его `render`.
- **Конкретная кнопка = использование.** `AddCharacterButton` и `PortraitButton` — это `Frame` + `Button` + контент с другими props, своей разметки кнопки у них нет; кнопки «Закрыть»/«Удалить» в шапке чарника отличаются от дефолтов только `color` и `onClick`. Если для новой кнопки хочется завести новый `.xml` — сначала проверьте, не хватает ли props.
- Состав повторяющихся блоков — данные, не разметка (правило 1). поля чарника описаны тегом `<Field name="field_x"/>` (и обёртками `<LabeledField>`/`<HeaderChip>`), а не копиями `<InputField>`: добавить поле = добавить строчку в разметку, тип контрола и значение тег возьмёт сам из `core/CharacterFields`.
- `builders/` — композиция экрана из компонентов, своей разметки там нет.

**Разметка — вся страница целиком, без слотов.** `ui/layout/specific/CharacterSheet.xml` — это лист персонажа как есть (`<Col id="character_sheet_root">`, шапка одним `<Row>`, тело — три колонки `2fr:3fr:3fr` с `<Section title="ATTRIBUTES">`), `ui/layout/specific/MainUI.xml` — весь экран (`<Anchor at="left" x="60"><PartyRail/></Anchor>` + `<CharacterSheet/>`). Отсюда и размер билдеров: `builders/UIBuilder.lua` — только контекст рендера.

Раскладка директорий (тёзок между ними нет — это была прошлая ошибка, когда обёртки лежали рядом с контрактами под теми же именами):

```
src/ui/
  Theme.lua                палитра, единственное место с цветами
  Component.lua            подстановка {{KEY}} + props/defaults
  Markup.lua               движок кастомных тегов + контекст рендера
  Layout.lua               решатель раскладки: <Row>/<Col>/<Box>/<Scroll>/<Anchor> -> TTS XML
  layout/
    reusable/*.xml         переиспользуемая разметка-компоненты
    specific/*.xml         экранная/доменная разметка (MainUI, CharacterSheet и т.д.)
  components/*.lua         контракты тегов: defaults + render(props)
  sheet/*.lua              теги, привязанные к данным персонажа
  generated/Templates.lua  ОДИН генерируемый файл со всей разметкой
  builders/UIBuilder.lua   сборка контекста
```

- **У каждого визуального компонента есть свой `.xml`.** Без разметки остаются только переключатели и композиции: `Field` (выбирает Text или InputField), `LabeledField` (две части), `ViewOnly`/`WizardOnly` (условия), `Common` (хелперы). `Label`/`Caption`/`Note` — один `TextLine.xml` с разными дефолтами, `Badge` — пилюля со значением. Списки (`Attacks`, `Features`, `InventoryList`, `SkillList`) своей разметки не имеют, но вид их строки — имеет: `AttackRow.xml`, `AttackEditRow.xml` и т.д. Правило: **в XML — вид, в Lua — только цикл, условие и вычисление**.
- Единственный допустимый слот `{{...}}` — результат цикла (`{{PORTRAITS}}` в `PartyRail.xml`): длину списка разметка знать не может. Структуру страницы слотами не собирают.
- **Контекст рендера**: `Markup.render(template, { character, party, mode, ... })`. `<Field name="field_name"/>` сам берёт значение из `core/CharacterFields`, тип поля и режим. `<CharacterSheet/>` сам решает, рисоваться ли, `<PartyRail/>` сам обходит партию.
- Цвета в разметке — **роли** Theme (`color="sheetBg"`), включая сырые теги TTS: роли разрешаются одним проходом по готовому XML в `Markup.render`. Литералы (`#hex`, `rgba(...)`) проходят мимо.

**Капканы движка (уже наступали):**
- Подстановка идёт **одним** проходом `gsub` через функцию-замену. Циклом `gsub` по ключам нельзя: в строке замены `%` и `%1` имеют особый смысл, и данные вида `Скидка 50%` рендерились с потерей процента, а `%1` подставлял обратно сам плейсхолдер (проверено на старой реализации). Плюс при последовательных заменах значение, содержащее `{{...}}`, попадало под подстановку на следующей итерации.
- **Имя кастомного тега не должно совпадать с тегом TTS.** Зарегистрировать `Button` или `Panel` нельзя: компонент рендерит `<Button ...>`, движок увидит в результате свой же тег и уйдёт в бесконечную рекурсию. Поэтому кнопка листа — `<SheetButton>`, а сырой `<Button>` в разметке остаётся сырым.
- **Бандлеры видят только `require` со строковым литералом.** Реестр тегов хранит не путь строкой, а функцию с литеральным `require` внутри: при `require(REGISTRY[name])` модули тегов просто не попадали в бандл (24 модуля вместо 66), и в игре тег упал бы на module not found. Ленивость при этом сохраняется — цикла загрузки нет.
- Сканер `tts_bridge.py` ищет `require` по сырому тексту, **включая комментарии**: литеральный `require` с многоточием внутри комментария роняет бандлинг (наступали).
- Кастомный тег отдаёт `content` только компоненту, который его объявил в `defaults`; иначе падает с внятным сообщением (у `Tile` содержимое приходит в `value`, и безусловный `content` ронял бы `<Tile/>`).
- `Component.props` падает на неизвестном ключе: в песочнице TTS нет линтера, и опечатка `onclick=` вместо `onClick=` иначе проявится только мёртвой кнопкой. `Component.render` падает на плейсхолдере, для которого не передали значение.
- Строка в Lua — байты. `name:sub(1, 1)` от «Мира» отдавал половину кириллической буквы, и весь XML становился невалидным UTF-8 (в портрете — мусор). Первый символ берётся как ведущий байт + продолжения (`firstCharacter` в `UIBuilder`).
- Фрагмент из двух корневых элементов — невалидный XML, и редактор будет ругаться на файл, который вы же и правите. Такие связки собираются в Lua (`LabeledField` = `FieldLabel` + контрол), а не отдельным `.xml`.

**Поля листа — один реестр.** `core/CharacterFields.lua` знает про каждое поле две вещи: как прочитать значение из модели и как записать (плюс `kind` — `text`/`integer`/`csv`/`multiline`, по нему UI выбирает контрол). Раньше это жило в двух копиях — список значений в рендерере и `if`-цепочка `updateCharacterField` в `Global.lua` на 90 строк — и они разъезжались; теперь и лист, и обработчик правки ходят в реестр, а `Global.lua` — 130 строк. Индексированные семейства (`field_attack_2_damage`, `field_item_1_qty`, `field_equip_mail`) разбираются шаблоном, поэтому реестр не надо расширять под каждую строку списка. Подписи и порядок полей — не в реестре, а в `ui/layout/specific/CharacterSheet.xml`: это лейаут, а не модель.

**Капкан:** у всех индексированных семейств подпись строго `(character, capture1, capture2, value)`. У слотов экипировки второй захват не нужен, но параметр обязателен — иначе `value` уезжает в него и запись молча теряется (уже наступали).

## Правило 4 — core/ui разделены, UI реактивен

- **`src/core/`** — модель и сервисы. `Store.lua` — общий реактивный контейнер состояния (`setState` + `subscribe`, ничего не знает про TTS UI). `PartyService.lua` — модель партии + методы-намерения (`selectCharacter`, `openCharacterSheet`, `closeCharacterSheet`, `setActiveTab`, `useAbility`, ...). `core/` никогда не вызывает `UI.setXmlTable` и вообще не знает о существовании XML/кнопок.
- **`src/ui/`** — `Builders.lua` (чистые функции state → xmlTable, без побочных эффектов), `HUDView.lua` (подписывается на `PartyService`, на каждое изменение стейта перерисовывает весь UI целиком — реактивно, сам не хранит и не мутирует состояние), `HUDEvents.lua` (единственное место с глобальными `onClick`-колбэками TTS — парсит id элемента и **только** зовёт метод сервиса, не мутирует и не рендерит сам).
- Поток всегда один: **XML-клик → `HUDEvents` → `PartyService`-метод → `Store:setState` → уведомление подписчиков → `HUDView` перерисовывает**. Ни один слой не имеет обратной стрелки (UI никогда не трогает `Store` напрямую, `core` никогда не знает про XML).
- То же самое будет верно для будущих сервисов (сейвы через `PersistenceService`, бой через `CombatService` и т.д.) — кнопка "Сохранить" в UI вызывает `PersistenceService.save()`, а не пишет файл сама.

**Известный Lua-капкан:** `store:setState({ field = nil })` **не** сотрёт `field` — конструктор таблицы `{ key = nil }` вообще не создаёт ключ, `pairs()` его не увидит. Для явного сброса поля в nil — `store:setState({ field = Store.NULL })` (sentinel, см. `core/Store.lua`).
